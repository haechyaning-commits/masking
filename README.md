# 공공감사포털 업로드 전 개인정보 마스킹 도구

감사데이터를 공공감사포털에 올리기 전, 문서의 개인정보를 **자동 탐지 → 사람 검토 → 마스킹 PDF 저장**하는 **브라우저 단독 실행 도구**입니다. 설치·서버·인터넷 없이 동작하며, 파일이 외부로 전송되지 않습니다.

> **1차 필터링 도구**입니다. 자동 탐지는 오탐·누락이 있을 수 있으니 결과물을 **반드시 육안으로 최종 확인**한 뒤 업로드하세요.

## 프로젝트 소개

공공기관 감사실에서 인턴으로 근무하며 겪은 문제(감사파일 업로드 전 개인정보를 수기로 하나씩 가리는 작업)에서 착안해 개인적으로 만든 프로젝트입니다. 소속 기관의 공식 도구가 아니며, 실제 감사파일이나 내부 자료는 사용하지 않았습니다 — 보안상 실데이터로 검증할 방법이 없어, "이런 게 있으면 실무에 도움이 되겠다"는 아이디어를 허구 데이터로만 구현·검증한 상태입니다. 그래서 이 도구를 설계할 때는 자동화의 정확도보다 **"화면엔 가려진 것처럼 보이는데 실제로는 원본이 복구 가능한 상태"라는 실패를 구조적으로 막는 것**을 최우선 목표로 삼았습니다 (자세한 내용은 [보안](#보안-데이터를-어떻게-지키는가) 섹션 참고).

## 바로 쓰기

- **웹으로 바로 쓰기**: <https://haechyaning-commits.github.io/masking/> — 링크만 열면 바로 사용(설치·다운로드 불필요). 저장소 Settings → Pages에서 활성화해야 열립니다(Source: `main` 브랜치의 `/docs` 폴더).
- **완전 오프라인 실행**: `web/masking-standalone.html` 파일을 내려받아 **더블클릭** → 인터넷을 완전히 끊어도 동작. 매우 민감한 문서를 다룰 때, 혹은 "코드가 실제로 바뀌지 않는다"는 걸 스스로 확인하고 싶을 때 선택하세요.
- 두 버전은 **완전히 동일한 코드**이며(빌드 시 함께 생성), 어느 쪽을 쓰든 브라우저가 네트워크 전송을 강제로 차단합니다 — 아래 [보안](#보안-데이터를-어떻게-지키는가) 참고.
- 사용 흐름: PDF 업로드 → 탐지 결과 검토 → (필요 시) 이름·기관 입력·직접 지정 → 마스킹 수준 선택 → **마스킹 PDF 생성/다운로드**.
- 시험용 샘플: `samples/복무감사_결과보고서_샘플.pdf`, `samples/2023_정기감사_결과_처분요구서_샘플.pdf` (모든 개인정보가 가공된 허구 데이터. 후자는 각 기관 자체감사규정 별지서식 등 공개된 감사결과 처분요구서 표준 구성을 참고해 만듦 — 두문(수신·참조)·처분요구 총괄표·관련자 인적사항 표·법인카드 사용내역 등 포함).

## 기능

### 1) 번호류 자동 탐지 (정규식)
주민등록번호·전화번호·이메일·계좌번호·카드번호를 자동 탐지. 공백·점·전각숫자 등 표기 변형에도 대응.

### 2) 이름·기관/부서 (기호 치환)
형식이 없어 정규식만으로는 탐지가 어려운 이름·기관은 다섯 가지 신호를 조합해 처리:
- **가릴 단어 목록 입력** — 입력한 이름/기관을 문서 전체에서 찾아 치환
- **접미어 규칙 자동** — 센터·사무소·구청·주식회사·병원 등으로 끝나는 이름의 앞부분 자동 탐지 (접미어는 유지: `서울복지센터` → `○○○○센터`)
- **성명 라벨 자동** (기본 켜짐) — 「성명:」, 「작성자」, 「피감사자」 같은 서식 라벨 바로 뒤의 한글 이름을 문맥으로 탐지. 사전이 없어도 정확도가 높아 기본으로 켜둠(「성명이 …」처럼 라벨이 문장 속 일반명사로 쓰인 경우는 구분자가 없어 자동으로 제외되고, 「담당자 이메일:」처럼 라벨 뒤에 이름이 아니라 또 다른 항목명이 오는 경우도 걸러냄)
- **표 열 구조 자동** (기본 켜짐) — 감사보고서에 가장 흔한 표 형태 명단("연번·소속·성명·…" 열 헤더가 맨 위에 한 번만 있고 각 행에는 라벨 없이 이름만 있는 구조)을 위한 탐지. PDF 안의 각 글자 조각이 가진 좌표를 이용해 "성명"류 열 헤더의 x좌표를 찾고, 그 아래로 같은 열에 있는 칸을 전부 이름 후보로 채택한다(표를 만드는 도구 대부분이 칸마다 별도로 텍스트를 그린다는 점에 기반함 — 셀 구분 없이 통짜 텍스트로 된 표에는 적용 안 됨). 실제 표준 서식 샘플 2건(총 5개 표, 20개 이름)으로 검증해 전부 정확히 탐지하고 오탐 없음을 확인
- **이름 사전 자동탐지 (베타, 기본 꺼짐)** — 흔한 한국 성씨로 시작하는 낱말을 이름 후보로 추정. 문맥 없이 사전만으로 판단해 오탐 가능성이 있어(감사 문서에 흔한 "예산", "판단", "위반" 같은 낱말은 제외 목록으로 걸러내지만 모든 경우를 다 잡지는 못함) 기본은 꺼두고, 켠 경우 검토 화면에서 「사전·베타」 표시가 붙은 항목을 꼭 확인할 것을 권장

### 3) 직접 지정 (클릭 / 드래그)
- 자동이 놓친 단어를 **클릭**하면 마스킹. **"같은 단어 모두 가리기"** 로 문서 전체 일괄 처리.
- 표·도장 등 비텍스트 영역은 **드래그**로 지정. 추가 항목은 다시 **클릭하면 삭제**.

### 4) 마스킹 수준 — 부분 / 전체 선택
**부분 마스킹(표준·권장)** 은 국내 공공기관 실무 기준을 따릅니다:

| 항목 | 가리는 부분 | 예 |
|---|---|---|
| 주민등록번호 | 뒤 7자리 | `990101-*******` |
| 전화·휴대폰 | 뒤 4자리 | `010-1234-****` |
| 이메일 | 아이디 앞 3자만 남김 | `abc***@sr.co.kr` |
| 계좌번호 | 앞 6자리만 남김 | `110-234-******` |
| 카드번호 | 앞 6·뒤 4자리 유지 | `123456******1234` |
| 이름 | 가운데 글자 | `홍*동` |
| 기관·부서 | 접미어 앞 전부 | `○○○○실` |

**전체 마스킹** 은 값 전체를 가림(번호=검은박스, 이름·기관=마스킹 기호). 번호류 마스킹 문자(`*` 기본, ○·△·□·♠ 선택)는 바꿀 수 있고, **이름·직접지정(문자 방식)은 사람(단어)마다 다른 기호**(`○●△▲□■◇◆☆★` 순환 배정)가 자동으로 붙어, 같은 표 안에 여러 사람이 있어도 서로 다른 인물임을 구분할 수 있습니다(실제 공공기관 문서의 `김○○`·`이△△` 관례 참고). 같은 사람은 문서 전체에서 항상 같은 기호를 씁니다.

### 5) 출력
결과는 **페이지 이미지화**로 저장되어 마스킹된 원본 글자가 추출되지 않으며, 원본 PDF 메타데이터도 제거됩니다.

### 6) 스캔본 인식 (OCR)
텍스트 레이어가 없는 페이지(스캔한 이미지 PDF)를 만나면 자동으로 [Tesseract.js](https://github.com/naptha/tesseract.js)(한국어 fast 모델)로 OCR을 시도합니다. 인식된 글자마다 실제 좌표를 갖고 있어서, 이후 탐지·마스킹 파이프라인은 일반 PDF 텍스트와 동일하게 동작합니다(오히려 글자마다 실측 박스를 쓰기 때문에 부분 마스킹 폭 추정이 더 정확할 때도 있습니다).
- **번호류(주민번호·전화·계좌·카드·이메일)는 실제 문서로 검증했을 때 잘 잡힙니다.**
- **이름 자동탐지(성명 라벨·표 열 인식·사전)는 OCR 페이지에서 정확도가 떨어집니다** — 한글은 음절(글자 하나하나)이 시각적으로 뚜렷이 분리돼 있어 Tesseract가 붙어 있는 한 단어도 여러 조각으로 잘못 나누는 경우가 실측에서 흔했습니다(모델을 fast→best로 바꿔도 동일). 코드에서 픽셀 간격 기반으로 다시 이어 붙이도록 보정했고, 표 열 인식도 이 보정된 결과(글자 단위)를 다시 칸 단위로 합쳐 동작하도록 손봤습니다. 다만 표 헤더가 **진한 배경색 위 흰 글자**로 돼 있으면 표 열 인식이 앵커를 못 찾는 경우가 있습니다. 진한 배경 영역이 있으면 색을 반전한 사본도 함께 인식해 병합하도록 시도해봤지만, 실제로 검증해보니 반전본으로도, 페이지 분할 모드를 바꿔봐도 이런 헤더는 여전히 인식되지 않아 — "밝은 배경/어두운 글자 전제" 라는 원래 추측이 틀렸다는 것만 확인했고 진짜 원인은 아직 못 찾았습니다(로드맵 참고). 스캔본의 이름은 **직접 지정(클릭/드래그)**을 함께 쓰는 걸 권장합니다.
- 완전 오프라인 실행을 위해 Tesseract 코어(WebAssembly)·한국어 학습데이터까지 전부 파일 안에 내장했습니다(네트워크 요청 없음 — 아래 [보안](#보안-데이터를-어떻게-지키는가) 참고). 그 대가로 파일 용량이 커집니다(공식 저장소 기준 약 2MB → 약 8MB).

## 보안 (데이터를 어떻게 지키는가)

- **완전 클라이언트 사이드**: 파일은 브라우저 메모리에서만 처리됩니다. 코드에 업로드/네트워크 전송(fetch·XHR 등)이 **전혀 없습니다**.
- **외부 의존 0**: pdf.js·pdf-lib를 파일 내부에 포함(CDN 없음) → **인터넷을 끊어도 동작**합니다(이것이 곧 "데이터가 밖으로 나가지 않는다"는 증거).
- **CSP로 브라우저 차원에서 강제 차단**: `connect-src 'none'` 등을 명시한 [Content-Security-Policy](https://developer.mozilla.org/ko/docs/Web/HTTP/CSP)를 페이지에 넣어뒀습니다. 코드를 읽어서 "정말 fetch가 없는지" 사람이 매번 확인하지 않아도, **브라우저가 기술적으로 모든 네트워크 요청을 차단**합니다 — 코드가 나중에 변조되더라도 데이터 전송 자체가 불가능합니다. (OCR 기능을 위해 `script-src`에 `'wasm-unsafe-eval'`을 추가했는데, 이건 "이미 파일 안에 들어있는 WebAssembly 모듈을 브라우저가 컴파일하도록" 허용하는 것뿐입니다 — `eval()`·`Function()` 같은 일반 동적 코드 실행(`'unsafe-eval'`, 별개 토큰)은 여전히 막혀 있고, `connect-src 'none'`도 그대로라 네트워크 차단에는 영향이 없습니다.)
- **진짜 삭제**: 출력이 이미지화라 마스킹 부분의 원본 텍스트가 남지 않습니다(아래 트레이드오프 참고).

### 설계 트레이드오프 (왜 이렇게 만들었나)

이 도구가 마주치는 실패의 종류는 딱 하나, **"화면엔 가려진 것처럼 보이는데 실제로는 원본 개인정보가 복구 가능한 상태"** 입니다. 아래 두 가지 결정은 전부 이 실패를 피하는 방향으로 내린 것입니다.

**1) 왜 텍스트를 진짜로 지우지 않고, 페이지 전체를 이미지로 다시 그리나?**
검은 박스로 "덮기만" 하고 원본 글자가 PDF 안에 그대로 남아있으면, 전체 선택(Ctrl+A)이나 텍스트 추출 프로그램으로 가려진 정보가 그대로 복사됩니다. 실제로 이런 방식의 "가짜 마스킹"이 텍스트 추출로 뚫려 정부 문서가 유출된 사례가 여러 번 있었습니다. PDF 내부 명령어를 직접 파싱해서 특정 글자만 도려내는 "진짜 삭제"도 기술적으로 불가능한 건 아니지만, 폰트 인코딩(특히 한글 CID/Type0 폰트)·압축 스트림 등 예외가 많아 실패 시 **눈에 안 띄게 원본이 남는** 최악의 결과로 이어질 수 있습니다. 그래서 지금은 pdf.js·pdf-lib만으로 안전하게 구현 가능한, 페이지 전체를 래스터화해 원본 텍스트 레이어 자체를 없애는 방식을 씁니다. (Adobe Acrobat 등 정식 리댁션 도구도 같은 원리를 씁니다.) 대가로 결과물은 이미지가 되어 용량이 커지고 텍스트 선택이 안 됩니다.

**2) "클라이언트 사이드=무조건 안전"은 아닙니다**
"파일이 서버로 안 간다"는 것과 "코드를 믿을 수 있다"는 건 별개 문제입니다. 이 도구가 실제로 막는 것과 못 막는 것을 구분하면:
- ✅ **막음**: 파일이 어딘가로 전송되는 것 (fetch 자체가 없고, CSP로 브라우저가 이중으로 차단).
- ✅ **막음(웹 호스팅본 포함)**: 서버가 나중에 코드를 몰래 바꿔서 데이터를 빼돌리는 것 — CSP가 코드 내용과 무관하게 네트워크 요청을 차단하므로, 매번 코드를 재검증할 필요가 없습니다.
- ❌ **못 막음**: 사용자의 브라우저나 브라우저 확장 프로그램이 이미 악성코드에 감염된 경우 (이건 어떤 웹 도구도 못 막습니다).
- ❌ **못 막음**: 정식 보안 감사·펜테스트를 거치지 않은 개인 프로젝트라는 점 — 실데이터로 쓰기 전 직접 검토하시길 권합니다.
- **완전 오프라인 실행본**(`web/masking-standalone.html`)은 위 CSP에 더해, 다운로드한 그 순간의 코드가 이후로도 절대 바뀌지 않는다는 것까지 보장합니다 — 극도로 민감한 문서라면 이쪽을 쓰세요.

## 지원 범위 / 한계

- **지원**: 텍스트 레이어가 있는 PDF. 스캔본(이미지) PDF도 OCR로 시험 지원(번호류는 실측 검증됨, 이름은 정확도 낮음 — 위 [6) 스캔본 인식](#6-스캔본-인식-ocr) 참고).
- **미지원**: HWP(별도 PDF 변환 선행 필요), 세로쓰기.
- **한계**: 사람 이름 등 비정형 정보는 완전 자동이 아니며(직접 입력/클릭 필요), 정규식 특성상 오탐·누락 가능. 좌표는 근사이며 회전 페이지는 정확도가 떨어질 수 있음.
- **OCR 한계**: 해상도가 낮거나 손글씨인 스캔본은 인식률이 크게 떨어짐. 현재 한국어 fast 모델 하나만 내장(영어·숫자는 같은 모델로 인식되나 다른 언어 문서는 지원 안 함).
- **표 열 구조 인식의 한계**: 칸마다 별도 텍스트 조각으로 그려진 표뿐 아니라, 공백 3칸 이상·탭 문자로만 칸을 나눈(조각이 안 나뉜) 표도 지원한다. 다만 그 구분자 자체가 아예 없는 표(예: 고정폭이 아니라 좌표만으로 정렬해 칸 사이에 어떤 구분 문자도 없는 경우)는 여전히 지원 밖이며, 이런 경우는 라벨 규칙이나 직접 지정(클릭)에 의존해야 한다. 또한 표 중간에 빈 칸·특이한 값이 섞여 있으면 그 지점에서 탐지가 멈출 수 있다(표 전체가 아니라 이름처럼 보이는 칸이 연속되는 구간까지만 인식).

- [x] 표준 부분/전체 마스킹 선택
- [x] 이름·기관 기호 치환 + 직접 지정(클릭/드래그)
- [x] 이름 자동탐지 — 성명 라벨 규칙(기본) + 성씨 사전 규칙(베타, 오탐 가능)
- [x] 표준 공개 서식(감사결과 처분요구서) 기반 샘플로 1차 검증 — 오탐 2건 발견·수정(쉼표로 끊긴 금액 뒤 계좌번호가 전화번호로 오탐되던 문제, "감사담당자 연락처"처럼 라벨이 다른 낱말에 붙어 다음 낱말을 이름으로 오탐하던 문제)
- [x] 표 열 구조 인식 — "성명" 등 열 헤더의 좌표를 찾아 그 아래 칸을 전부 이름으로 탐지(라벨 없이 표만 있는 명단에 대응). 실제 PDF 두 건(pdfjs-dist로 직접 파싱)에서 표 5개·이름 20건 전부 정확히 탐지, 오탐 0건 확인
- [x] 스캔본 OCR 시험 지원(Tesseract.js, 한국어 fast 모델 완전 내장) — 번호류는 실제 문서로 실측 검증, 이름 자동탐지는 정확도 낮음을 확인하고 문서화. CSP `connect-src 'none'`을 유지한 채(네트워크 요청 0회) 오프라인 실행 파일(`file://`)·GitHub Pages(`http(s)://`) 양쪽에서 실제로 동작하는 것까지 확인(오프라인 실행 파일에서는 워커 안에서 별도 코어 스크립트를 불러오는 방식이 origin 문제로 실패해, 코어+워커를 하나의 Blob으로 합치는 방식으로 수정)
- [x] 표 열 인식이 OCR 결과(글자 단위 item)에서도 동작하도록 보정 — 같은 줄 안에서 글자 사이 간격이 좁으면(진짜 표 열 사이 간격보다 훨씬 좁음) 하나의 칸으로 합치는 로직 추가. 기존 PDF 텍스트 샘플 2건(표 5개·이름 20건)으로 회귀 검증해 오탐 없이 동일하게 동작함을 확인. 다만 실제 OCR 샘플로 검증하다 **더 근본적인 별개의 문제**를 발견함 — 표 헤더 셀이 진한 배경색 위 흰 글자(다크 스타일)로 돼 있으면, 이 병합 로직과 무관하게 **OCR 자체가 헤더 문구를 거의 인식하지 못함**(Tesseract는 기본적으로 밝은 배경/어두운 글자를 전제로 함). 병합 로직 자체는 검증됐지만, 색 대비(polarity) 문제가 먼저 해결돼야 어두운 헤더가 있는 실제 표에서 효과를 볼 수 있음
- [x] OCR 색 대비(polarity) 보정 시도 — 진한 배경 영역이 있으면(값싼 샘플링으로 사전 확인) 이미지를 반전한 사본도 함께 OCR하고, 신뢰도(confidence) 기준으로 두 결과를 병합(NMS 방식)하도록 구현함. 다만 **실제 다크 헤더 샘플로 검증한 결과, 이 방법으로는 문제가 해결되지 않았다**: 원본·반전본 모두, 그리고 페이지 분할 모드를 강제로 바꿔봐도(균일 텍스트 블록 모드) 다크 헤더 문구는 여전히 인식되지 않음 — 즉 "밝은 배경/어두운 글자를 전제로 한다"는 처음 가설이 **틀렸다**는 뜻. 실제 원인은 아직 못 찾음(진한 배경색 자체·글자 굵기·특정 렌더링 조합 등 추가 조사가 필요). 병합 코드 자체는 안전하게 남겨둠(진한 배경이 없는 페이지는 원래대로 1회만 인식해 속도 영향 없음, 다른 원인의 다크 배경 문서에는 도움이 될 수도 있음)이나, 이번에 만든 샘플의 다크 헤더 문제는 **여전히 미해결**로 남음 — 그런 표의 이름은 직접 지정(클릭)에 의존해야 함
- [ ] 다크 배경 헤더가 OCR에서 인식되지 않는 진짜 원인 조사 — 색 반전으로는 해결 안 됨을 확인(위 항목). 렌더링 해상도를 더 높여보거나, Tesseract의 이진화(binarization) 파라미터를 직접 조정하는 등 다른 접근이 필요
- [ ] 이름 정식 NER 자동탐지(문맥·품사 기반)
- [x] 셀 구분 없는(공백 3칸 이상·탭 문자로만 나뉜) 표의 열 인식 지원 — 표 전체 행이 칸별 조각(item)으로 안 나뉘고 "성명    소속    연락처"처럼 한 덩어리 텍스트로 된 문서(단순 텍스트를 그대로 PDF로 찍어낸 경우 등)에서, 그 구분자를 기준으로 가짜 조각(virtual item)을 만들어 기존 표 열 인식 로직에 그대로 태움. x좌표는 글자 수 비율로 나눈 근사치이지만(열 구역 판정에만 쓰이고, 실제 마스킹 박스는 원본 조각의 실측 글자 폭으로 그려져 최종 정확도엔 영향 없음), 손으로 만든 표 4행 시나리오로 이름 3건 전부 정확히 탐지되는 것을 확인. 기존 실제 PDF 샘플 2건(표 5개·이름 20건)도 회귀 검증해 동일하게 동작함을 확인(정상 문서에서는 이 분리 로직이 아무 영향도 주지 않음 — 보통 칸 안에 공백 3칸 이상이 없기 때문)
- [x] HWP 지원 재검토 — 순수 JS로 HWP/HWPX를 SVG로 변환하는 오픈소스 라이브러리(`hwp-to-svg` 등)를 조사함. 브라우저 API(DOMParser·XMLSerializer·IndexedDB) 기반이라 구조적으로는 이 도구에 붙일 수 있어 보이나, 두 가지 이유로 **보류**함:
  - HWPX(zip+XML, 공공기관 2020년 이후 표준 포맷)조차, 실제 한글 프로그램이 저장 시 미리 계산해 넣는 문단·줄 위치 정보(`lineseg vertpos` 등)가 파일 안에 있어야 레이아웃이 제대로 잡힘 — PDF 샘플처럼 이 도구가 직접 표준 라이브러리(reportlab)로 완전히 통제해서 만드는 것과 달리, 한글 프로그램의 내부 계산을 흉내내야 해서 검증 없이 만든 샘플로는 실제 문서와 같다고 보장할 수 없음
  - 이 세션에는 한컴오피스가 없고, 후보 라이브러리 저장소에도 테스트용 샘플 파일이 없어 **실제 파일로 검증할 방법이 없었음**(오늘 다른 기능들은 전부 실제 파일 기반으로 검증한 것과 대비됨)
  - 구 버전 바이너리 HWP(OLE/CFB 기반)는 더 복잡해 검증 없이는 더더욱 위험 판단
  - 결론: 실제 HWP/HWPX 샘플 파일(허구 데이터로 된 것도 무방)을 구할 수 있게 되면 재검토. 그 전까지는 기존 안내대로 **외부에서 PDF로 변환 후 사용**을 권장

## 개인정보 처리 안내

업로드한 PDF와 마스킹 결과는 **브라우저 내에서만 처리**되며 외부 서버로 전송·저장되지 않습니다.
